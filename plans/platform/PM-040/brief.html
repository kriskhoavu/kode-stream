Knowledge learns the shape of a wiki

A wiki more than two directories deep lost most of its graph to a single point and became unreadable as a tree. PM-040 infers bucket, area and tier from the directory layout, then groups both Knowledge views by them — capping the hierarchy at two levels whatever the wiki's depth.

The short version

The layout was always readable — the meaning was hardcoded

A restructured wiki does not break Knowledge today. Every page still carries slug and title, the root still has index.md, and domain already tolerates arbitrary nesting. What breaks is narrower and worse: the app has no idea that domains is a subject bucket while concepts is a tier, so twenty distinct path strings arrive flat. And one bucket's meaning is written into the service as the literal e2e-testing, which makes the wiki's own naming a load-bearing part of the code.

After PM-040, tiers are detected from within-bucket recurrence, each page carries bucket, area and tier, and the journey lookup asks for the bucket holding the journeys role. A workspace with no settings file behaves exactly as it does now, because that role defaults to e2e-testing. domain is untouched, so no surface changes and nothing under web/ is edited.

Figure 1

Where you count parents decides whether the rule works

Detecting tiers means finding directory names that repeat. The obvious version of that test counts parents across the whole tree, and it fails on the reference wiki: offer appears under both domains and e2e-testing, so a naive count promotes a subject area to a tier. Counting inside a single bucket separates the two cleanly.

Figure 2

Detection cannot live where every other page rule lives

Every existing page rule runs inside ParsePage, once per file. The tier rule cannot: it is a property of the whole page set, and a single file carries no evidence of what repeats. So detection runs after the walk completes, alongside ResolveRelationships, which is the one point where the page slice is finished and warnings are still open.

Figure 3

The literal becomes a default, so nothing has to migrate

Removing a hardcoded string usually means every existing installation needs new configuration. Here it does not. The journeys role falls back to a bucket named e2e-testing, so a workspace that never gains a settings file resolves to exactly the pages it resolves to today.

Figure 4

One taxonomy, consumed by both views

Detection happens once, in the indexer, and both views read the result through one shared module — which is what stops the tree and the graph drifting into two different ideas of the hierarchy. domain survives untouched for breadcrumbs, and parser.go is not in play, so the front matter contract every page depends on is unaffected.

Delivery

Backend first, then the two views that consume it

B1 and B2 touch nothing shared. B3 is the join and the first contact with indexer code. B5 is the one backend change the views needed. F1 and F2 are independent of each other; F3 restyles what both produce, so it lands last.

Area absorbs anything the rule does not recognise

Segments appearing after a matched tier fold into the area rather than being discarded. A layout deeper or stranger than the reference wiki therefore degrades into a longer area string instead of silently losing a path component — which matters because the taxonomy is inferred, and inference on an unfamiliar tree will sometimes be wrong.

Scope

Deliberately not included

  • Front matter freshness. The restructured wiki adds lastVerified and claim-status marking to every page, and parser.go ignores both. That is schema work on the struct every page flows through, not layout configuration, and it earns its own ticket rather than riding along with this one.
  • Chunk metadata. The chunkId and keywords comments are pure retrieval signal and are currently discarded. Worth capturing, but it changes what the agent can find rather than how pages are organised.
  • The wiki appearing as cards in Workstream. That comes from wiki/workspace-settings.yaml, whose path pattern turns each top-level wiki directory into an item card. It is a scanner concern with nothing to do with Knowledge grouping, so it stays out until looked at on its own.

Open

One decision resolved, one still open

Resolved: the compatibility default needed a second branch

The literal e2e-testing turned out to exist in exactly two places in the Go codebase — both the planned call sites — with no other route in or under web/. But defaulting the bucket name was not sufficient on its own: an index written before PM-040 carries no bucket on any page, so matching on bucket alone returned no journeys at all until a rescan. Resolution now falls back to the page path when bucket is empty. The existing full-stack API test is exactly that case, and removing the fallback makes it fail — so the branch is load-bearing rather than defensive.

Should a detected taxonomy be sticky, or re-derived every scan?

As written, the taxonomy is inferred fresh on each rescan, so a growing wiki can see concepts shift from area to tier the moment a second area acquires one. That is arguably correct — the evidence genuinely changed — but it means classification is not stable over a wiki's lifetime. The alternative is writing detected values back into the settings file once confident, as the source-structure proposal flow already does for cards. That is more machinery and one more thing that can be stale. Deferred until the instability is observed rather than predicted. Owner: the ticket that first surfaces bucket and tier in the UI, since it is the first thing that would visibly flicker.
